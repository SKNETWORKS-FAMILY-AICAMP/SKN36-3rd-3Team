# 다음 팀원에게: 정책 데이터 작업 인수인계

기준: 2026-11-25, GitHub `dev`의 [PR #36](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN36-3rd-3Team/pull/36)까지 반영한 상태.

## 1. 기존에는 어떤 상황이었나?

- PR #36이 서울·경기·전북 목록과 12개 지역을 합쳐 **15개 지역 정책 4,278건**을 만들었습니다. 예전 경기 목록에서 비어 있던 상세정보 485건도 이미 연결했습니다. 이 원본은 `data/staging/local_welfare/2026-11-25/`에 있습니다.
- 그다음 검색 준비 단계는 아직 예전 **574건** 자료를 사용했습니다. 예전 자료에서는 API의 조회수(`inqNum`)가 문의처처럼 적힐 수 있었습니다.
- 예전 574건에만 있던 전남 라벨 **149건**은 PR #36에서 별도 파일에 보존했습니다. 이번 4,278건의 원본과 섞으면 출처를 확인하기 어렵습니다.

**비유:** PR #36이 여러 상자의 서류를 한 권의 **새 주소록**으로 합쳤는데, 검색기는 아직 **옛 주소록**을 보고 있던 상황입니다.

## 2. 이번에는 어떻게 작업했나?

| 작업 | 쉬운 설명 | 위치 |
|---|---|---|
| 조회수 오류 수정 | 가게 **방문자 수**를 전화번호로 적지 않도록 막음 | `src/welfare_preprocessing/`, `src/rag/`, `scripts/load_postgres.py` |
| 새 검색 후보 만들기 | PR #36의 주소록을 받아 지역·노인 관련성으로 분류하고 검색용 문서를 다시 만듦 | `scripts/build_local_welfare_candidate.py` |
| 변경 후보 비교 | 새 주소록과 옛 주소록을 비교해 새 정책·달라진 정책·사라진 듯한 정책을 검토표로 만듦 | `scripts/diff_local_welfare_snapshots.py` |
| 안전장치 | 잘못된 번호, 지역 불확실성, 오래된 자료와 새 자료의 혼합을 막음 | `backend/`, `frontend/`, `tests/` |

PR을 올리면 수정 파일 전체는 **Files changed**에서 볼 수 있습니다. 생성한 100MB 이상의 검색 후보 파일은 PR에 넣지 않았습니다. 코드는 저장소의 기존 `src/`, `scripts/`, `tests/`, `docs/`에 배치했습니다.

## 3. 그래서 결과는?

| 결과 | 의미 |
|---|---|
| **4,278건** 입력 → **1,778건** 노인 관련 검색 후보 | 사람 검토 전의 후보 숫자입니다. 실제 신청 대상 1,778건이라는 뜻은 아닙니다. |
| **1,487건** 추가 검토, **1,013건** 제외 후보 | 버리지 않고 따로 보관했습니다. |
| A 방식 **4,754개**, B 방식 **5,240개** 검색용 분할 자료 | 정책 문서와 기존 PDF 4종을 함께 사용해 ID 연결을 검사했습니다. |
| 새 검색 문서의 잘못된 문의처 **0건** | 원본에 확인된 전화번호가 없으므로 비워 두었습니다. |

PR #36의 보고서 해시는 Windows 줄바꿈으로 계산됐지만, GitHub에 저장된 파일은 LF 줄바꿈입니다. 두 파일이 **줄바꿈만 다를 때만** 검증을 통과하도록 처리했습니다. 검증 파일의 해시와 GitHub 파일의 해시는 실행 결과 `manifest.json`에 각각 남습니다.

**중요:** 이 결과는 검토용 폴더에만 생성됩니다. PostgreSQL·Qdrant·Neo4j와 서비스 화면의 실제 정책 데이터는 이 작업으로 바뀌지 않습니다.

### 직접 확인하는 명령

프로젝트 루트에서 실행합니다. 테스트에는 `pytest`, `pydantic`이 필요합니다.

```bash
python -m pytest tests/test_data_integrity.py tests/test_pg_loader.py -q
python -m scripts.build_local_welfare_candidate --output-dir ./review-output
```

`review-output/run_.../manifest.json`은 어떤 원본을 썼는지, `candidate_report.json`은 몇 건을 처리했는지 보여줍니다. 생성 파일은 검토용입니다. `--apply`로 운영 DB에 바로 넣지 마세요.

**한 문장으로:** 새 주소록을 읽는 검색용 후보까지 만들었습니다. 이제 팀이 서류를 확인하고 승인한 뒤, 새 주소록과 검색기를 같은 버전으로 교체해야 합니다.
