## 1. 목적과 검증 범위

사용자가 일상적인 말로 복지정책을 물었을 때 **적합한 근거를 검색하고, 그 근거 안에서 답하며, 필요한 조건과 출처를 안내하는지** 검증한다. 검색 결과에 정답 문서가 있는지와 생성된 답변이 정확한지는 별도로 측정한다.

```text
질문·세션 → 입력 및 안전 확인 → 의도 확인 → 정책·안내서 검색
         → 근거 충분성 확인 → 답변과 출처 또는 확인 질문·안내
                                 ↘ 선택적으로 PostgreSQL 대화 기억
```

팀의 기존 평가 계획은 검색 정확성, 근거 일치, 쉬운 설명, 조건 확인, 정보 부족 대응, 최신성 점검을 목표로 삼았다. 아래 계획의 세부 항목은 작성 근거에 따라 구분했다. [팀 평가 계획](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN36-3rd-3Team/blob/4b172752b87282fe4bae89f8b212d11e493b6d78/docs/evaluation.md)

- **기존 계획·테스트** — T01·T07은 기존 검사와 단위 테스트를 따른다. T02의 모델 선정 기준은 실험 노트북에 사전 기준으로 기록돼 있다.
- **실행 기록에서 재구성** — T02의 세부 조건과 T03·T04의 절차를 실행 자료에서 정리했다. T05·T06과 T09의 모의 오류 검사는 검토 중 수행한 사례에서 기대 동작과 판정 범위를 정리했다.
- **후속 검증** — T08의 실제 답변 평가, T09의 운영 실측 및 T05의 HTTP·화면 재검증은 앞으로 적용할 절차다.

## 4. 지표 정의와 집계

| 지표 | 문항별 계산 및 집계 |
| --- | --- |
| Hit@K · MRR@5 | Hit@K는 채점 문항 중 상위 K개 검색 결과에 정답 근거가 하나라도 나온 비율이다. MRR@5는 첫 정답의 역순위 평균이다. 예를 들어 첫 정답이 2위면 0.5, 상위 5에 없으면 0이다. T02는 청크 순위에서 부모 ID를 비교하고, T03은 처음 등장한 부모만 남긴 순위를 사용한다. |
| Recall@5 · Recall@10 | T02는 상위 5청크에서 찾은 서로 다른 정답 부모 ID 수를 전체 정답 후보 ID 수로 나눈다. T03 복수 문항은 상위 10개 안에서 후보를 하나라도 찾은 정답 묶음 수를 전체 묶음 수로 나눈다. 문항별 값을 평균한다. |
| Precision@10 | T03 복수 문항의 상위 10개 중 실제 반환한 부모를 분모로, 정답 묶음에 포함되는 반환 부모를 분자로 한다. 빈 결과는 0이다. 문항별 값을 평균한다. |
| 지역·함정 통과 | T02는 금지 ID 유입, 지역 정책 반환, 빈 응답을 따로 기록한다. T03 최신 채점은 금지 ID 0건 또는 자료가 없는 지역의 지자체 정책 노출 0건을 판정한다. 답변 기권 확인이 필요한 문항은 미채점으로 남기며 시설 전용 문항은 제외한다. |
| 검색 시간 | T02는 채점 검색 루프의 경과 시간을 채점 문항 수로 나눈다. T03은 각 문항의 검색 함수 실행 시간을 기록한다. 평균·중앙값·p95는 시간값이 있는 문항만 사용하며, 이 보고서의 p95는 오름차순에서 `ceil(0.95 × n)`번째 값이다. 두 값 모두 최종 답변 생성 시간과 구별한다. |
| 답변 정확성·근거 적합성(후속) | 답변 가능 문항마다 기준 사실과 필수 조건을 지정한다. 정확도는 기준을 충족한 답변 수 ÷ 답변 가능 채점 문항 수, 근거 적합성은 공식 근거로 지지되는 검증 대상 주장 수 ÷ 전체 검증 대상 주장 수로 집계한다. 답변 불가 사례는 적절한 확인 질문·기권 건수 ÷ 해당 채점 문항 수로 따로 센다. |
| 운영 성공률·응답 시간(후속) | 기대 응답과 상태를 받은 요청 수 ÷ 전체 유효 테스트 요청 수를 계산한다. 클라이언트 요청 시작부터 전체 응답 수신까지를 재고 평균·중앙값·p95와 실패 건수를 함께 기록한다. 의도적으로 넣은 오류 시나리오는 정상 부하 집계와 구분한다. |

## 5. 재현 절차와 기록

1. **입력을 고정한다.** 질문 파일, 청크, 벡터, 코드 커밋과 해시를 기록한다. T03은 v3·ABC·페르소나 순서로 질문을 구성한다. 반복 측정 시 실행 순서, 모델 준비 시간, 캐시와 동시 요청 조건도 기록한다.
2. **저장 데이터와 기능을 확인한다.** 데이터 로더의 검사 전용 모드로 파일 간 참조를 확인한다. 기존 데이터 매핑·세션 단위 테스트는 프로젝트 밖의 쓰기 가능한 임시 경로에서 수행한다. 모의 API는 `CHAT_API_MOCK=true`에서 정상·오류 입력을 비교한다. 실제 연결을 확인한 결과는 모의 결과와 구분해 기록한다.
3. **검색 실험을 재현한다.** T02는 임베딩 A/B 노트북의 전체 실행으로 네 조합을 돌리고, T03은 평가 브랜치 노트북에서 세 안을 실행한다. 기존 서비스 DB와 분리한 테스트 데이터에서 수행하고 결과 파일은 별도 위치에 저장한다. 문항별 반환 ID·순위·시간·제외 사유와 요약표를 함께 보관한다.
4. **답변을 별도로 평가한다.** T08은 기준 답변·출처와 비교해 자격·금액·신청 방법을 확인한다. LLM을 평가자로 쓰면 버전·평가 문구를 고정하고 표본을 사람이 교차 검토한다. 이번 자료에서는 답변 평가 모델과 결과가 확인되지 않았다. T09는 정상과 장애 조건에서 각 실행의 요청 수·반복 횟수·동시성·타임아웃을 기록한다.
5. **결과를 판정한다.** 문항마다 입력 ID, 기대 근거 또는 행동, 관찰값, 판정, 근거 위치를 남긴다. 모의 기능은 기대 동작과 일치하면 통과로 기록한다. 검색 점수와 속도는 비교값으로 보고하며, 팀 승인 목표치가 정해지면 적용 버전·표본과 함께 기록한다.
