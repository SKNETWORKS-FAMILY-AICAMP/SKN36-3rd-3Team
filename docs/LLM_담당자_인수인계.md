# LLM 담당자 인수인계 — 안전 판단 보완 메모

작성일: 2026-11-27

> 사용자 결정: RAG 구축을 먼저 진행하고, 추가 LLM 안전 판단은 이후 LLM 연결 단계에서 담당자에게 인계한다. 이 문서는 후속 작업 메모이며, 안전 기능 구현 완료나 서비스 전환 승인을 뜻하지 않는다.

**추가 결정(2026-11-27): 실제 긴급 상황을 일반으로 넘기는 누락을 우선 줄인다. 수정할 때마다 긴급 문장과 일상 함정 문장을 함께 시험해, 일반 질문을 긴급으로 잘못 잡는 오탐도 놓치지 않는다. 모든 질문을 긴급 처리해 누락만 없애는 방식은 사용하지 않는다.** 누락과 오탐은 별도 수치로 기록한다. 사용자는 추가 LLM 안전 판단을 후속 담당자에게 넘기고 다음 RAG 검색 코드 수정으로 진행하기로 했다.

## 1. 언제 연결하면 되나요?

RAG를 먼저 구축한 뒤 LLM 연결 시점에 안전 판단을 추가할 수 있다. 질문을 검색으로 보낼지 결정하는 앞단을 보완하는 작업이므로, 이 기능 때문에 기존 정책을 다시 청킹하거나 임베딩할 필요는 없다.

다만 실제 사용자 대상 시연·운영 전에는 안전 경로를 포함한 전체 연결 시험을 해야 한다. RAG 검색 시험 통과와 안전 기능 통과는 별도로 기록한다.

- RAG 담당: 지역·승인 버전 필터, 묶음별 검색, 검색 결과와 근거 전달을 우선 진행한다.
- LLM 담당: 질문의 의미·위험 신호 판단, 판정 결과 검증, 답변 지침 연결을 맡는다.
- 백엔드 담당과 협업: DB 장애 처리, 안전 경로 분기, 상담 안내, 대화 문맥·저장 범위를 연결한다.

## 2. 현재 확인된 한계

현재 안전 분기는 정규식 중심이다. 특정 표현을 발견하면 고정 안전 안내를 반환하고, 확인이 필요한 경우에는 답변 지침과 상담 안내를 붙이는 코드가 수정·검토 중이다.

| 확인 내용 | 해석할 때 주의할 점 |
|---|---|
| Claude가 공유한 개발용 안전 문항 30개는 30/30 일치 | 이미 본 문장을 맞힌 결과이며 일반적인 안전 성능을 뜻하지 않는다. |
| Codex 1차 새 문장: 15/30 일치, 긴급 3/12 탐지 | 이후 개발용으로 사용했다. 미공개 검증용으로 다시 보고하지 않는다. |
| Codex 2차 새 문장: 16/30 일치, 긴급 4/12·확인 먼저 2/8·일반 10/10 | 새 말투의 긴급 표현을 많이 놓쳤다. 지금은 이 세트도 공개되어 추가 개발에 사용하면 개발용이 된다. |
| 위 두 세트에서 긴급 오탐 0건으로 보고됨 | 해당 소규모 표본의 결과일 뿐이다. 다른 일상 표현에서도 오탐이 없다는 보장이 아니다. |
| 정규식 결과가 `normal` | 규칙에 걸리지 않았다는 뜻이다. 안전하다고 검증했다는 뜻이 아니다. |

안전 평가의 기대 단계는 팀 운영 기준이다. 사용자 확인을 받았다는 사실과 전문가가 위험도를 검증했다는 사실은 구분한다.

## 3. 나중에 추가할 LLM의 역할

새 모델을 반드시 별도로 도입하는 것은 아니다. 현재 질문 의도를 판단하는 LLM 호출에서 안전 판정도 함께 받는 방안을 우선 검토한다. 기존 호출과 합칠 수 있다면 추가 호출 횟수를 줄일 수 있지만, 지연·토큰 비용·정확도는 연결 후 측정한다.

```text
사용자 질문
    ↓
정규식으로 명확한 긴급 신호 확인
    ├─ 긴급 → DB·LLM·검색을 기다리지 않고 고정 안전 안내
    └─ 그 외 → LLM으로 질문 의도와 위험 신호 해석
                  ├─ 긴급 → 사유에 맞는 고정 안전 안내
                  ├─ 확인 필요 → 필요한 확인 질문과 안내 우선
                  └─ 일반 → RAG 검색 → 근거 확인 → 답변 생성
```

연결할 때 지켜야 할 규칙:

1. 정규식이 잡은 긴급 신호를 LLM이 일반 단계로 낮추지 못하게 한다.
2. LLM 판정은 허용한 단계·사유만 받도록 형식을 검사한다. 임의의 진단명이나 자유 서술을 분기 값으로 사용하지 않는다.
3. 위험 사유에 따라 안내를 구분한다. 사기 질문에 자해용 문구를 내보내지 않는다.
4. LLM 실패·잘못된 JSON·시간 초과를 안전 확인 성공으로 처리하지 않는다. 판정 불가 시 동작을 별도로 정하고 시험한다.
5. 정규식이 놓친 경우에도 DB 장애가 의미 판정까지 막지 않도록 대화 기록을 필수 선행 조건으로 만들지 않는다.
6. 이전 대화가 필요한 짧은 질문을 다룬다. 긴급 대화를 저장하지 않는 기존 원칙과 후속 안전 확인의 문맥 유지 방법을 함께 정한다.
7. 확인 질문이 필요한 경우, 검색 근거가 없거나 의도 분류가 실패해도 필요한 질문과 안내가 나오도록 한다. 상담 전화만 덧붙이는 것으로 완료 처리하지 않는다.

정확한 판정 필드와 입력·출력 계약은 LLM 담당자와 연결 시 확정한다. `urgent / distress / normal`은 현재 코드 값이고, 평가 파일의 `check_in`은 현재 `distress`에 대응한다.

## 4. 추가 LLM과 별도로 처리할 기존 코드 문제

2026-11-27 Codex 코드 검토에서 아래 사항을 수정 요청했다. **추가 LLM 작업을 뒤로 미루는 결정이 이 오류들을 그대로 두어도 된다는 뜻은 아니다.** 후속 수정·재검토 여부를 인계 시 다시 확인한다.

| 검토 사항 | 필요한 확인 |
|---|---|
| 문장 안의 과거 표현 하나가 현재 응급 신호까지 무시하게 함 | 과거와 현재 증상을 함께 말해도 현재 신호가 사라지지 않는가 |
| 이웃 관련 단어가 있으면 현재 직접 폭력도 제보로 낮춰질 수 있음 | 장소·주변 사람과 실제 피해자·현재 상황을 구분하는가 |
| 정상적인 주사 접종·주택 구매 표현을 긴급으로 잡을 수 있음 | 다의어·부정문·일상 문맥을 오탐하지 않는가 |
| 의도 응답·근거 부족 종료 경로에서 사유별 확인 질문이 빠질 수 있음 | 모든 종료 경로와 LLM 오류에서도 필요한 안전 질문이 나오는가 |

현재 구현 상태는 최신 코드와 테스트로 다시 확인한다. 이 메모는 해당 문제가 이후에도 미수정 상태라고 단정하는 기록이 아니다.

**수정 상태 (2026-11-27, Claude 기록)**: 위 4건은 같은 날 `src/agents/safety.py`에서 수정했고 `tests/test_safety.py`에 재현 문장을 테스트로 넣었다(커밋 전, 수정 뒤 Codex 재검토는 받지 않음).

| 검토 사항 | 수정 내용 | 테스트 |
|---|---|---|
| 과거 표현이 현재 응급 신호를 가림 | 과거 여부를 문장마다 따로 봄 (`_emergency_now`) | `test_past_event_does_not_hide_current_emergency` |
| 이웃 단어가 있으면 직접 폭력도 제보로 낮춰짐 | 말하는 사람 자신이 당하는 경우(`_ABUSE_SELF`)를 제보보다 먼저 판정 | `test_own_abuse_wins_over_neighbor_report` |
| 주사 접종·주택 구매 표현을 긴급으로 잡음 | "맞고 있/계" 꼴 제외, 목적어 뒤의 "살 생각이 없"은 제외 | `test_words_with_two_meanings` |
| 일부 종료 경로에서 확인 질문이 빠짐 | 사유별 확인 질문과 상담 전화를 마무리 노드(`safety_note_node`)가 항상 붙임 | `test_every_distress_reason_asks_a_question` |

남아 있는 한계는 2절 그대로다. 새 말투의 긴급 표현 누락(2차 문장에서 긴급 12개 중 4개 탐지)은 정규식 보강으로 해결되지 않았다.

## 6. 연결 완료 기준

- 정규식으로 잡힌 긴급 질문은 DB·LLM·Qdrant·Neo4j 장애 시에도 고정 안내가 나온다.
- LLM이 긴급으로 판정한 질문은 정책 검색보다 안전 안내로 먼저 분기한다.
- 확인 필요 질문은 의도 분류·근거 검사·답변 생성의 각 종료 경로에서도 필요한 질문과 안내가 유지된다.
- 정상적인 은행 업무·주사 접종·과거 병력·부정문·일반 복지 질문의 오탐을 검사한다.
- 판정 단계뿐 아니라 위험 사유와 실제 응답 내용도 검사한다. 전화번호 포함 여부만으로 통과시키지 않는다.
- DB 장애, LLM 오류·시간 초과·잘못된 JSON, 검색 장애를 실제로 주입해 결과를 기록한다.
- 개발에 쓰지 않은 새 문장으로 일반화 시험을 한다. 개발용·검증용 결과를 분리하고 누락과 오탐을 함께 보고한다.
- 기존 RAG 검색과 정상 질문 답변이 회귀하지 않는지 확인한다.

후속 담당자는 이 문서와 최신 코드·평가 기록을 먼저 읽고 연결 계획을 제시한다. 모델 변경, 추가 API 비용, 민감한 대화 저장 방식 변경은 구현 전에 사용자와 합의한다.

## 7. RAG 담당이 의도 확인 지시문을 고친 내용 (2026-11-28)

사용자 결정으로 RAG 담당(Claude)이 [intent_check.py](../src/agents/intent_check.py)의 `INTENT_PROMPT`만 최소한으로 고쳤다. 코드 흐름, LLM 오류 시 기본 동작(clarify), 안전 판정은 바꾸지 않았다. 의도 확인 수정은 별도 커밋 `092fb4dc8cadbdc2f4709b241f58bc77edee305a`에 저장했다. 담당자가 지시문을 다시 짤 때 그대로 두거나 되돌릴 수 있게 하려는 것이다.

### 왜 고쳤나

| 문항 | 앞 대화 | 사용자 말 | 고치기 전 | 고친 뒤 (4차 전체 흐름) |
|---|---|---|---|---|
| V004 | 횡성군 식사 배달 사업 안내 | "그럼 나는 무조건 받는 거지?" | 검색 없이 "무엇이 궁금하세요? 1. 신청 방법…" 메뉴 | 검색 후 "무조건은 아니고 저소득·결식 우려 어르신이 대상, 가족복지과(전화번호)에 확인" |
| V024 | 강북구 안부 사업 안내 + 수급 여부 질문 | "말하기 싫어." | 검색 없이 "1. 직접 연락받기 싫어요…" 메뉴 | 수급 여부를 다시 묻지 않고 사업 2개의 일반 대상·신청처 안내 (40~64세 사업은 나이 밝힘) |

### 바꾼 내용 (규칙 3묶음)

| 규칙 | 내용 |
|---|---|
| `[앞 대화에 이어진 짧은 질문]` | 바로 앞 답변이 특정 제도를 안내했고 "나도 돼?", "무조건 받지?", "어떻게 신청해?"처럼 그 제도를 가리켜 물으면 search. 검색어는 앞 대화의 제도·지역 + 궁금한 것. 앞 답변을 확인된 사실로 보지 않고 다시 검색함. 앞 대화가 없거나 가리킬 제도 이름이 없으면 적용하지 않고, 화면 지역이 있어도 clarify (지역 이름만으로 "복지 지원 대상" 같은 막연한 검색 금지) |
| `[개인 정보 질문에 대한 답]` | 소득·수급 여부 등을 물었는데 "말하기 싫어"(거부)나 "잘 모르겠어"(모름)라고 하면 같은 질문을 반복하지 않고 앞 주제로 search. 거부·모르는 정보는 검색어에 넣거나 추측하지 않음. 모름이면 검색어에 "지원 대상 확인 방법"을 덧붙임 |
| `[예외: 지역을 물은 경우]` | "어느 지역 기준으로 찾아 드릴까요?"에 지역을 고르지 않고 "모르겠어요" 등으로 답하면 clarify 유지 (엉뚱한 지역 정책 안내 방지) |

되돌리려면 `INTENT_PROMPT`에서 위 세 이름으로 시작하는 묶음을 지우면 된다.

| 3차 방식 V004·V024 (Neo4j가 꺼져 있어 Qdrant만) | 둘 다 의도 확인은 search. V024는 답변, V004는 3차 자료에서 근거를 못 찾아 "찾지 못했어요"로 끝남 | `chat_flow_legacy_vector_r1_intent.json` |

13문장에는 되물어야 맞는 질문("나 배고파", "힘들어", 앞 대화 없는 "그럼 나도 받을 수 있어?"), 새 주제("근데 틀니도 지원돼?"), 범위 밖("오늘 날씨 어때?"), 일반 제도 안내, 지역을 물었을 때 "모르겠어요"가 함께 들어 있다. 처음 시험 도구는 화면 지역을 잘못된 키로 넣어 지역 없이 시험됐다. 고친 뒤 다시 재니, 첫 지시문은 앞 대화 없는 "그럼 나도 받을 수 있어?"를 화면 지역만 보고 검색해서 12/13이었다. 그래서 위 첫 묶음에 "앞 대화가 없으면 clarify" 문장을 더했다.

점검 도구도 고쳤다. 나이 표시 점검이 "만 40~64세"만 알아보고 "40~64세"는 놓쳤다. 또 나이 제한 사업을 답변에서 아예 언급하지 않은 경우는 "해당 없음"으로 따로 센다(`age_limit_not_applicable`). 위 3/3·4/4는 고친 기준으로 다시 센 값이다.

### 알아 둘 부수 효과와 남은 일

- 예시 문구 영향으로 다른 질문의 검색어도 짧아지고 "어르신"을 쓰는 쪽으로 바뀌었다(예: "…혼자 사는 노인을 위한 식사 배달 서비스나 밥 지원 방법" → "…어르신 식사 배달 서비스 지원 방법"). 15문항에서 검색 결과는 나빠지지 않았지만, 지시문을 다시 짤 때 확인할 것.
- 지역을 물었는데 "모르겠어요"라고 한 경우 분류(clarify)는 맞다. 하지만 확인 질문이 지역 대신 도움 종류를 묻는다. 기존 지침 "화면에서 고른 지역은 다시 묻지 말 것"과 겹치기 때문이다.
- 의미 기반 안전 판정과 의도 확인 지시문 전반의 개선은 여전히 LLM 담당 몫이다. 지시문을 고칠 때마다 `scripts/eval_intent_followups.py`(13/13 유지)와 V004·V024 전체 흐름을 회귀 시험으로 돌린다.
