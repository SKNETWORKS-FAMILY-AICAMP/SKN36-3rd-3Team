### 우리 팀의 권장 데이터 형식

정부·기관 자료를 확보하면 한 정책을 아래처럼 정리한다. **아래 값은 이해를 위한 구조 예시이며 실제 정책 정보가 아니다.**

```json
{
  "policy_id": "EXAMPLE-001",
  "title": "정책명",
  "agency": "공식 제공기관",
  "region": "서울 또는 전국",
  "target_age": "공식 원문에 적힌 대상 연령",
  "eligibility": "지원 대상과 제외 조건",
  "benefit": "지원 내용",
  "application": "신청 방법과 문의처",
  "source_url": "공식 원문 URL",
  "checked_at": "자료 확인 날짜",
  "valid_until": "마감일이 확인되면 기록, 아니면 미확인"
}
```

**왜 이렇게 하나?** 자료를 그냥 통째로 넣으면 “지원 대상은 누구인지”, “아직 신청 가능한지”를 구분하기 어렵다. **원문(설명을 위한 텍스트)**과 **조건(필터에 쓸 데이터)**을 함께 관리하면 질문에 맞는 정책을 더 정확하게 찾을 수 있다.

## 4. 사용 기술과 RAG 구현 방식 확인

### RAG는 실제로 어떻게 돌아갈까?

**비유:** RAG는 *책을 읽지 않고 대답하는 상담원*이 아니라, **질문을 들으면 먼저 공식 책장에서 관련 페이지를 찾아 읽고 답하는 상담원**이다.

```text
[사전 준비: 1번 만들어 두는 과정]
공식 API·PDF·웹 문서 수집
   → 불필요한 내용 제거·정리(전처리)
   → 읽기 좋은 크기로 나누기(청킹)
   → 문장의 뜻을 숫자로 바꾸기(임베딩)
   → 검색용 데이터베이스(Chroma)에 저장

[사용자가 질문할 때마다 실행]
질문 입력
   → 지역·연령·핵심 표현 확인
   → 관련 문서 3개 정도 검색
   → AI가 검색된 자료만 참고해 쉬운 답변 생성
   → 정책명·출처 링크·확인일 표시
   → 근거가 없거나 조건이 부족하면 추가 확인 요청
```

| 기술·방식 | 쉽게 말하면 | 선배 사례 | 7일 MVP 적용 판단 |
|---|---|---|---|
| **공식 API / JSON** | 기관이 정해진 형식으로 제공하는 자료를 가져옴 | 20기 1팀, 29기 5팀 | **필수에 가까움**. 단, 승인 지연 시 이용조건 확인한 공식 PDF·HTML로 대체 |
| **청킹(Chunking)** | 긴 문서를 검색하기 좋은 단락으로 나눔 | 21기 1팀, 24기 3팀 | **필수**. 자격·제외 조건을 엉뚱하게 잘라내지 않기 |
| **임베딩 + ChromaDB** | “노후 생활비”와 “기초연금”처럼 뜻이 비슷한 문장을 검색 | 20기 1팀, 29기 5팀 | **필수**. 우선 벡터 검색 하나부터 작동시키기 |
| **메타데이터 필터** | 서울 정책인지, 대상 연령이 맞는지 등 명시된 조건으로 거름 | 20기 1팀, 29기 5팀 | **권장**. 원본 값이 확실할 때만 사용 |
| **BM25 / 하이브리드 검색** | 뜻이 비슷한 문장 검색에 정책명 같은 정확한 단어 검색을 더함 | 20기 1팀, 21기 1팀 | **시간 남으면**. 기본 검색보다 좋아지는지 측정 후 도입 |
| **검색 부족 처리** | 적합한 근거가 없으면 추측 대신 확인이 필요하다고 설명 | 29기 3팀, 30기 4팀 | **필수**. 신뢰성의 핵심 |
| **쉬운 답변 + 출처** | 누구에게 어떤 도움인지, 어디서 신청하는지 순서대로 설명 | 28기 1팀, 2기 5팀 | **필수**. 답변 뒤 공식 링크 표시 |
| **GraphRAG / 멀티에이전트** | 자료 사이 관계를 연결하거나 AI 역할을 여러 개로 나눔 | 28기 1팀, 29기 5팀 | **이번 주 제외**. 복잡성에 비해 MVP 이득이 불확실 |

| 적용할 것 | 왜 중요한가? | 우리 팀의 실제 작업 |
|---|---|---|
| **① 공식 출처 기록** | AI가 잘못 말했을 때 원문으로 확인할 수 있음 | 정책마다 기관명·URL·확인일 저장, 답변에 함께 표시 |
| **② 문서 정리·청킹 품질** | 필요한 근거가 검색되지 않으면 AI도 제대로 설명할 수 없음 | 지원 대상·제외 조건·신청 방법이 문서에서 끊어지지 않게 분리 |
| **③ 지역·연령 조건 구분** | 엉뚱한 지역이나 다른 연령 정책이 나오지 않도록 함 | 확인된 조건만 간단히 필터링, 모르면 추가 질문 |
| **④ 근거 부족 시 정직한 답변** | 없는 지원금·자격을 지어내면 신뢰가 깨짐 | “현재 자료로 확인하기 어렵습니다” 및 공식 문의처 안내 |
| **⑤ 검색 성능을 숫자로 비교** | 우리가 RAG를 제대로 구현했다는 근거가 됨 | 같은 30문항으로 기본 검색과 개선안 검색 결과 비교 |

### B. 우리 팀만의 작지만 분명한 차별점

**추천 차별화: “어르신 표현까지 이해하는 공식 정책 RAG + 개선 전후 검증”**

- 예시 질문: **“동사무소에서 받을 수 있는 노후 생활비 지원이 있나요?”**
- **1단계:** `동사무소 → 행정복지센터`, `노후 생활비 지원 → 기초연금 등 관련 정책`처럼 검색 표현을 정리한다. 이때 특정 제도에 해당한다고 **미리 확정하지 않고 후보를 검색**한다.
- **2단계:** 필요한 지역·나이 정보가 없으면 짧게 추가로 묻는다.
- **3단계:** 공식 문서에서 근거를 찾고, 지원 대상/신청 방법/원문 링크를 보여준다.
- **4단계:** 표현 정리 **전·후에 관련 정책이 상위 3개 검색 결과에 얼마나 자주 포함됐는지** 비교한다.

**장점:** 지도·음성·복잡한 AI 에이전트 없이도, **우리만의 문제 정의 → 개선 방법 → 객관적 평가**를 발표할 수 있다.

### C. 7일 프로젝트에 맞춘 5명 역할 분담 (권장안)

| 담당 | 핵심 책임 | 제출할 결과물 |
|---|---|---|
| **팀장 (1명)** | 범위 확정, 일정 관리, 코드 통합, 품질 점검, 발표 구성 | 통합 실행 체크리스트, 최종 발표·시연 시나리오 |
| **팀원 A** | 공식 정책 데이터 조사·확보·정리 | 원본 자료, 공통 정책 JSON/CSV, 출처·날짜 목록 |
| **팀원 B** | 청킹·임베딩·ChromaDB·기본 검색 | 검색 인덱스 생성 코드, `search(query)` 동작 |
| **팀원 C** | 검색 근거 기반 답변·추가 질문·오류 처리 | 답변 생성 모듈, 출처 포함 응답 형식 |
| **팀원 D** | Streamlit 최소 화면, 평가 자동화·결과 정리 | 질문·답변·출처 화면, 30문항 비교표 |

**서로 연결되는 순서:** **A가 정책 데이터를 전달 → B가 검색 결과를 전달 → C가 답변을 생성 → D가 화면·평가에서 보여줌 → 팀장이 통합 테스트.** 각자만 실행되는 코드가 아니라 마지막에는 **하나의 질문이 끝까지 처리**돼야 한다.

### D. 7일 작업 계획: 매일 무엇이 완료돼야 하나?

| 날짜 | 핵심 작업 | 그날 끝났을 때 확인할 것 |
|---|---|---|
| **D1** | 정책 범위·자료 출처 확정, 역할 나누기 | 공식 데이터 후보와 공통 JSON 필드 결정 |
| **D2** | 실제 정책 데이터 수집·정제, 최소 화면 틀 | 정책 원문·출처가 저장되고 샘플 입력 가능 |
| **D3** | 청킹·임베딩·검색·답변 최초 연결 | **질문 → 실제 근거 검색 → 답변 → 원문 링크** 1건 성공 |
| **D4** | 조건 처리·쉬운 답변·예외 처리 | 서울/연령 누락, 관련 자료 없음 등의 상황 확인 |
| **D5** | 30문항 평가, 오류 분석, 검색 개선 | 기본 검색 대비 개선 검색의 결과표 완성 |
| **D6** | 기능 고정, 통합 오류·보안·시연 점검 | 다른 팀원 PC에서도 실행 절차 재현 가능 |
| **D7** | 시연 리허설·발표·최종 PR 정리 | 실제 질문 3~4개로 전체 RAG 흐름과 평가 결과 시연 |

> **우선순위 규칙:** D3에 기본 RAG가 연결되지 않았으면 BM25·지도·음성·꾸미기는 중단한다. D6부터는 새 기능을 추가하지 않는다.

### E. 어떻게 평가해서 발표할까?

**30문항 평가셋(권장 구성):** 일반 정책 질문 15개 + 쉬운 말/옛 용어 질문 5개 + 지역·연령 등 조건 부족 5개 + 자료에 없거나 만료된 정책 질문 5개.

| 평가 항목 | 쉬운 뜻 | 측정 방법 |
|---|---|---|
| **상위 3개 검색 적중률(Hit@3)** | 정답 근거가 검색 결과 3개 안에 들어왔는가? | 정답 문서를 미리 지정하고 30문항 중 적중한 비율 계산. 대상 문서가 있는 질문만 분모에 포함 |
| **출처 일치** | 답변의 핵심 사실이 공식 자료에 실제로 있는가? | 지원 대상·금액·신청 방법·링크를 표본별로 확인 |
| **조건 누락 대응** | 지역·연령을 모를 때 함부로 단정하지 않는가? | 관련 5개 질문에서 추가 질문 또는 확인 필요 안내 여부 확인 |
| **근거 없는 답변 방지** | 검색 실패·만료 자료에 대해 꾸며 말하지 않는가? | 관련 5개 질문에서 보수적으로 응답하는지 확인 |

**발표 화면 예시(결과 수치는 실제 평가 후 입력):**

```text
질문: “동사무소에서 노후 생활비 지원 받을 수 있나요?”

기본 검색  → 상위 3개에 정답 근거 없음
개선 검색  → 표현 정리 후 상위 3개에 공식 근거 포함

AI 답변    → 쉬운 설명 + 필요한 조건 + 공식 출처 링크
평가 결과  → 30문항에 대해 기본/개선 검색을 같은 기준으로 비교
```

*이 예시는 시연 방식 설명이며 실제 측정 결과를 뜻하지 않는다.*

### F. 최종 권고: 이번 주에는 무엇을 하지 않을까?

**하지 않음:** 전국 모든 복지정책 수집, Neo4j·GraphRAG, 여러 LLM 에이전트, 음성 입출력, 지도, 로그인, 복잡한 프런트엔드, 파인튜닝, 서버 배포 고도화.

**반드시 보여줌:** **① 공식 자료를 어떻게 구했는지 → ② 어떻게 나누고 저장했는지 → ③ 어떻게 찾았는지 → ④ 어떻게 출처 있는 답변을 만들었는지 → ⑤ 얼마나 개선됐는지**.
