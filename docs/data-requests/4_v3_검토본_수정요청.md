## 1. 적용 지역을 "후보"로 채우기

**지금**: 시군구에 등록된 정책이 `candidate_scope=sigungu`만 있고 나머지는 비어 있습니다.

```json
"sido_name": "인천광역시", "sigungu_name": "연수구",
"candidate_scope": "sigungu", "applies_to": [], "scope_status": "unknown", "scope_basis": null
```

**바꿀 모습** (예: `local:WLF00000010`):

```json
"candidate_scope": "sigungu",
"applies_to": [{"sido": "인천광역시", "sigungu": "연수구"}],
"scope_status": "candidate",
"scope_basis": "원본 sggNm=연수구"
```

- 근거: 1번 요청서 R-3 기본 규칙. "구에 등록 = 확정"이 아니라 **후보**입니다. `region_scope`는 `unknown` 그대로 둡니다.
- 대상: 정상 시군구가 있는데 `applies_to=[]`인 정책 3,993건. 통합시 471건도 같은 규칙입니다.
- 원문이 등록 시군구와 다른 범위를 말하는 정책은 채우지 말고 미해결 목록에 이유를 적습니다.
- `region_changes.jsonl`에 `applies_to`, `scope_status`, `scope_basis` 줄을 추가합니다.
- `old` 값은 기준 파일 값 그대로 적습니다. 전국 기준 정책은 세 칸이 아예 없으므로 `null`입니다. 통합시 정책은 생성본 값(`applies_to`는 `[]`, `scope_status`는 `"unknown"`, `scope_basis`는 `null`)입니다.

**이유**: 지금은 `applies_to`가 채워진 정책이 37건뿐이라, 이 칸으로 지역 검색을 하면 대부분의 지역 정책이 빠집니다.

## 2. 시군구 칸의 교육청·`-` 값 비우기

**지금**: 통합시 2건만 고쳐졌고, 다른 시도는 그대로입니다.

| 값 | 건수 | 예 |
|---|---|---|
| `○○교육청` | 97건 (노인 후보 46건) | `local:WLF00001191` → `인천광역시교육청` |
| `-` | 9건 (노인 후보 2건) | `local:WLF00000126` |

**바꿀 모습**: `sigungu_name=null`. 원문 값은 `raw_sigungu_name`에 이미 있으니 그대로 둡니다.

- 근거: 0-2 규칙 "행정구역이 아닌 값은 `raw_sigungu_name`에만", 1번 요청서 점검표 "교육청 등 0건".
- 이 정책들은 `candidate_scope`도 `sigungu`가 아니어야 합니다. 기준 파일에 `region_scope=sigungu`로 들어 있어서, 그대로 두면 생성 스크립트(40~41행)가 `candidate_scope=sigungu`를 자동으로 넣습니다. `sigungu_name → null` 줄과 함께 `region_scope → "unknown"` 줄(`old`는 `"sigungu"`)을 넣으면 막을 수 있습니다.
- 적용 범위는 본문 근거가 있을 때만 채우고, 없으면 `applies_to=[]`, `unknown`으로 둡니다. **시도 전체로 자동 배정하지 않습니다.**
- 대상 ID는 부록 A, B에 있습니다.

**이유**: 사용자가 구를 고르면 `인천광역시교육청`과는 영영 일치하지 않아 이 정책들이 검색에서 사라집니다.

## 3. 그래프 지역에 확인 상태·근거 넣기

**지금**: `policy_graph_entities.jsonl`의 `regions` 항목에 `scope_status`, `scope_basis`가 없습니다.

```json
"regions": [{"sido_name": "…", "sigungu_name": null, "scope": "unknown",
             "candidate_scope": "sigungu", "applies_to": [...],
             "region_status": "needs_review", "review_status": "needs_review"}]
```

**바꿀 모습**: 같은 항목에 `scope_status`, `scope_basis`를 추가합니다. 값은 최종 정책 레코드와 같아야 합니다.

- 예: `local:WLF00001428`은 정책 파일에 `scope_status=candidate`와 근거 문장이 있지만 그래프에는 후보 목록만 있습니다.

**이유**: 청크와 그래프가 같은 정책에 대해 다른 정보를 주면 안 됩니다.

## 4. 통합시 정책의 나이 조건 채우기

**지금**: 원문에서 나이를 찾았는데(`age_evidence` 있음) `age_min`·`age_max`가 비어 있고 그래프에도 나이 조건이 없습니다. 77건 모두 통합시 정책입니다.

```json
// local:WLF00000167
"age_min": null, "age_max": null,
"age_evidence": [{"field": "target_text", "raw_text": "만65세 이상", "value": 65, "operator": ">="}]
```

**바꿀 모습**: 기존 전국 정책과 **같은 규칙·같은 형식**으로 나이 칸과 그래프 나이 조건을 만듭니다.

- 근거가 여러 개이고 값이 서로 다르면 임의로 합치지 말고 각각 검토 대기(`needs_review`)로 남깁니다.
- 검증 보고서의 "나이값이 있지만 그래프 나이 조건이 없는 정책" 점검은 `age_evidence` 기준으로도 세어 주세요. 지금은 `age_min/max`만 봐서 0건으로 나옵니다.
- 대상 ID는 부록 C에 있습니다.

**이유**: 노인 대상 서비스라 나이 조건이 빠지면 대상 판단이 어긋납니다.

## 6. 그래프에 신청 방법 넣기 (새 요청)

인계서의 질문 "그래프에서도 신청 방법을 직접 조회해야 하나요?"에 대한 답입니다. **네, 4가지 모두 필요합니다.**

정책 청크가 여러 개로 나뉜 260건 중 134건은 신청 방법 줄이 첫 청크에 없습니다. 정책 ID로 한 번에 조회할 수 있어야 답변에 빠지지 않습니다.

`policy_graph_entities.jsonl`의 각 정책에 `application` 묶음을 추가해 주세요.

```json
"application": {
  "application_text": "…신청 본문 원문…",
  "application_method_name": "동 주민센터 신청",
  "application_required": true,
  "application_basis": {"source_url": "…", "quote": "…", "checked_at": "2026-11-26"}
}
```

| 지킬 것 | |
|---|---|
| 그대로 복사 | 같은 버전의 `final_v3` 정책 값과 같아야 합니다. 새로 가공하지 않습니다 |
| 없으면 `null` | `false`를 `null`로 바꾸지 않습니다. 빈 값을 "신청 불필요"로 바꾸지 않습니다 |
| 선행 조건 보존 | `application_basis.quote`의 조건 문장(예: "한부모가족으로 결정된 가구")을 줄이지 않습니다 |

Neo4j에 넣고 조회하는 부분은 RAG 담당이 맡습니다.
