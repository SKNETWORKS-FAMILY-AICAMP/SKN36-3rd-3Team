> **버전:** v0.2 · **기준일:** 2026-11-10 · **상태:** 팀 공유·검토용  
> **저장소:** `SKNETWORKS-FAMILY-AICAMP/SKN36-3rd-3Team` · 기준 브랜치 `dev`

## 1. 목적과 문서 기준

### 1.1 서비스 목적

고령자 및 보호자가 **자신의 지역과 생활 상황에 맞는 복지정책**을 자연어로 질문하면, 관련 정책·공식 PDF 근거·신청 방법을 **쉽게 이해할 수 있는 문장과 출처**로 제공한다.

- 서비스는 **정보 탐색 및 신청 준비 지원** 도구다. 수급 자격 확정, 실제 신청 대행, 정책의 법적·행정적 판단은 수행하지 않는다.
- 검색 결과의 **관련성**과 실제 **신청 자격**은 별개다. 미검증 지역·지원 조건은 확인 필요로 표시한다.
- 저장소의 파일 존재·코드 작성·PR 머지는 곧바로 데이터 내용의 정확성 또는 서비스 작동 완료를 뜻하지 않는다.

### 1.2 근거 및 변경 원칙

이 문서는 기존 `노인복지_RAG_요구사항정의서_v0.1`의 목적·요구사항 ID 체계를 이어받되, **2026-11-10 GitHub `dev` 점검 결과**와 팀이 협의한 구현 방향을 반영했다.

| 구현 중 | PR #24 Qdrant/임베딩 연습용 코드(아직 미머지), PostgreSQL 실제 적재, Neo4j 그래프, 서비스 연동 |

## 2. 사용자와 이번 프로젝트 범위

| 사용자 | 필요한 결과 |
|---|---|
| 고령자 | 쉬운 표현으로 정책명, 지원 내용, 신청 방법 및 출처 이해 |
| 보호자·가족 | 가족 상황과 지역을 반영한 정책 탐색과 준비사항 확인 |
| 개발·검수 담당자 | 원문 출처, 데이터 버전, 정책/청크 ID, 검색 성능 및 검수 상태 추적 |

### 2.1 이번 3차 프로젝트 포함 범위

1. **정책:** PR #25의 지자체 노인 관련 정책 선별 결과 **574건**. 현재 파이프라인은 서울·경기·전남 관련 후보 범위를 처리하지만, 개별 정책의 적용 지역이 확정되었다는 뜻은 아니다.
2. **PDF:** PR #26의 공식 지침 **4종**, 정규화된 **1,189개 섹션**. 문서별 출처·목차·PDF 파일 기준 페이지 범위를 보존한다.
3. **검색:** 정책 및 PDF 청크를 Qdrant에 임베딩하여 의미 검색하고, PostgreSQL에서 정책 상세·근거·청크를 조회한다.
4. **관계:** Neo4j에 검증된 정책–대상–지역–문서/섹션 등 노드·관계를 적재하고, 그래프 조회를 포함한 검색 방식과 제외한 방식을 비교한다. 실제 구현 가능한 최소 관계부터 시작한다.
5. **화면:** React + FastAPI 기반의 기본 챗봇 질의·응답·출처 표시를 목표로 한다.
6. **시설:** 기존 확보한 복지시설 데이터는 삭제하지 않고 **제한된 참고 데이터로 유지**한다. 지역별 자료 누락 가능성과 갱신 시점을 표시한다.

### 2.2 이번 프로젝트에서 제외 / 4차 프로젝트 후보

- **4차로 이관:** 대체 복지시설 API 선정·전면 재수집, 시설별 위치 좌표의 지도 맵핑, 사용자의 현재 위치 기준 주변 시설 추천, LLM의 방문 권유 기능 고도화.
- 현재 서울 시설 수가 적게 조회된다는 팀원 보고(약 13곳)는 **데이터 범위 제약 이슈**로 기록하되, 서울에 실제 시설이 13곳뿐이라는 사실로 설명하지 않는다.
- 현재 확보한 시설의 **신뢰 가능한 주소·좌표·갱신 정보가 부족하면**, 지도·거리·근처 추천 기능을 작동한다고 표시하지 않는다.
- 정책 직접 신청·승인 자동화, 수급 자격 확정, 검증되지 않은 정책–PDF–시설 관계를 사실로 단정하는 기능은 제외한다.
- PDF 5번째 자료 및 중앙부처 정책의 추가 확대는 **이번 완료 범위에 자동 포함하지 않으며**, 추가 결정 시 변경이력에 기록한다.

## 3. 전체 데이터 처리 및 서비스 흐름

### 3.1 자료 준비와 저장 (사용자 질문 이전)

```text
지자체 복지정책 OpenAPI ─→ PR #25 정규화·노인 관련 정책 선별 (574건)
                                  │
                                  └→ PR #26 정책 RAG 문서화

공식 PDF 4종 ─→ PDF 전처리·섹션 정리 (1,189건)
                                  └→ PR #26 PDF RAG 문서화
                                              │
                                   PR #26 청킹 A / B
                                   ├─ A_fixed: 3,400청크
                                   └─ B_structure: 3,865청크
                                              │
                  ┌───────────────────────────┼─────────────────────────┐
                  ▼                           ▼                         ▼
             PostgreSQL                    Qdrant                    Neo4j
       정책 상세/출처/청크 적재         청크 임베딩/의미 검색       검증된 노드·관계 적재
       (PR #25 + PR #26)           (모델×청킹 A/B 평가)        (관계 탐색 비교)
```

**중요:** PostgreSQL과 Qdrant에 공통으로 쓰는 `id`(UUID), `chunk_id`, `policy_id`, `section_id`는 **PR #26의 실제 데이터 규칙**으로 연결한다. 시설 데이터는 정책·PDF RAG 파이프라인과 별도 경로로 관리한다.

### 3.2 질문 처리 (구현 목표)

```text
React 사용자 질문
       ↓
FastAPI: 질문·지역·필요 조건 파악 (모르는 조건은 미상)
       ↓
질문 임베딩 → Qdrant: 유사 정책/PDF 청크 Top-k 검색
       ↓
검색 결과의 UUID 및 부모 ID로 PostgreSQL 원본/조건/출처 조회
       ↓
필요한 질문에서 Neo4j: 검증된 정책·대상·지역·근거 관계 탐색
       ↓
LLM: 관련 근거를 보강해 쉬운 답변 생성
       ↓
React: 정책명·지원 내용·신청 방법·출처·확인 필요 사항 표시
```

Neo4j는 모든 질의에 억지로 사용하지 않고 **관계 탐색에 유용한 질의**에서 활용한다. 관계 없는 질문에는 Qdrant + PostgreSQL만으로도 처리할 수 있게 설계한다. FastAPI가 세 저장소의 조회 결과를 조합하며, 저장소들이 자동으로 서로 호출하는 구조는 아니다.

| `data/rag/documents/guideline_documents.jsonl` | PDF 섹션 RAG 문서 | 1,189건 |
| `data/rag/documents/source_documents.jsonl` | PDF 출처 레지스트리 | 4종 |
| `data/rag/documents/guideline_sections_normalized.jsonl` | PDF 정규화 섹션·검수 | 1,189건 |
| `data/rag/chunks/A_fixed/{policy_chunks,guideline_chunks}.jsonl` | Fixed 청크 | 정책 662 / PDF 2,738 |

| `data/rag/chunks/step07_chunking_report.json` | 청크 건수·ID 무결성 검사 | **검색 성능 평가 아님** |

`run_...`는 해당 결과의 실행 폴더다. 새로운 실행 결과를 사용할 때는 파일 경로·수집 범위·변경 이력을 함께 업데이트한다.

### 4.2 ID 및 메타데이터 규칙

| 구분 | 실제 규칙 / 연결 방법 |
|---|---|
| 원본 정책 ID (PR #25) | `policy_id = servId` (예: `WLF...`) |
| RAG 정책 ID (PR #26) | `policy_id = local:{servId}` (예: `local:WLF...`) |
| 정책 원본 연결 | PostgreSQL 저장 시 원본 `servId`를 별도 보존하고, RAG용 `local:` ID를 공통 연결 키로 사용 |
| PDF 출처 ID | `document_id`: PDF 자료별 고정 문자열 |
| PDF 섹션 ID | `section_id`: PDF 전처리 단계 ID 유지 |
| 청크 논리 ID | `policy::{policy_id}::{fixed\|structure}::{0001...}` 또는 `guideline::{section_id}::{fixed\|structure}::{0001...}` |
| Qdrant 포인트 / SQL 청크 ID | `id = str(uuid.uuid5(uuid.NAMESPACE_URL, chunk_id))` — PR #26에서 제공한 값을 **재생성하지 않고 그대로 사용** |
| 청크 부모 ID | `metadata.parent_id`: 정책은 `policy_id`, PDF는 `section_id` |
| 공통 청크 구조 | `{id, chunk_id, text, metadata, policy_id 또는 section_id}` |

메타데이터는 원본 필드명을 기준으로 저장하며 **미검증 지역을 승인된 지역으로 바꾸지 않는다**. `region_code=null`, `region_selection_verified=false`, `region_review_status=pending/provisional`, `elderly_category=direct/indirect`는 지원 자격 승인 여부와 다르다. PDF의 `page_start/page_end`는 **부모 섹션의 PDF 파일 페이지 범위**이며, 반드시 해당 청크의 단일 정확 페이지를 뜻하지 않는다.

| 담당 | 핵심 역할 | 구현·검증 산출물 |
|---|---|---|

| **Qdrant/임베딩** | 청크 벡터화·의미 검색 및 모델 비교 | 청킹 A/B × 임베딩 모델 A/B **4조합 실험**, 전략/모델별 컬렉션, 검색 API에 넘길 청크 UUID·점수·메타데이터 |
| **Neo4j** | 근거 기반 노드·엣지 관리 및 관계 검색 | 관계 스키마, 검증된 노드/엣지 적재, Cypher 조회, Graph 사용/미사용 비교 결과 |
| **전처리/청킹** | 원본 보존, 문서화, 데이터 구조·품질 관리 | PR #25·#26 결과, 수정/갱신 시 입력 버전·ID 영향 전달 |
| **FastAPI/LLM** | 질의 조건 해석, 검색 통합, 답변·근거 생성 | Qdrant→PostgreSQL(+Neo4j) 검색 흐름, 미검증 정보 통제, 예외 처리 |
| **React/UI** | 고령자 친화적 질의·응답 표시 | 질문창, 정책 결과, 출처/신청 안내, 오류·정보 부족 안내 |
| **시설 데이터** | 기존 시설 정보 유지·품질 이슈 기록 | 현재 데이터 범위·출처·갱신 시점 표시; 4차 API/지도 고도화 이관 |

### 5.1 PostgreSQL 적재 원칙 — 팀 합의 반영

**기존 인수인계 문서의 SQL 권장 사항에 PR #25 정책 상세정보를 추가한다.**

- **정책 574건:** PR #25의 정규화 필드(`title`, `summary`, `target_text`, `selection_criteria_text`, `benefit_text`, `application_text`, `department`, `contact`, 지역·날짜·출처·검수 상태)를 `welfare_policies`에 저장한다. PR #26의 `policy_documents.jsonl`에서 검색용 `text`와 메타데이터를 함께 연결한다.
- **PDF:** PR #26의 `source_documents`, `guideline_documents` 및 섹션 정보를 `source_documents`, `guideline_sections`에 저장한다.
- **청크:** PR #26의 A/B 청크 **총 7,265건**의 `id(UUID)`, `chunk_id`, `record_type`, `parent_id`, `chunk_strategy`, `text`, `metadata`를 `rag_chunks`에 저장한다. A/B가 서로 다른 UUID를 갖도록 유지한다.
- **시설:** 기존 확보 데이터를 별도 테이블에서 관리하되, API 교체 또는 지도 좌표 확장은 4차 범위로 분리한다.
- **연결 테스트:** Qdrant의 UUID → `rag_chunks.id` → 정책은 `welfare_policies.policy_id`, PDF는 `guideline_sections.section_id` → `source_documents.document_id`를 조회한다.
- `rag_chunks.parent_id`는 정책/지침을 동시에 가리키는 키이므로 조회 시 **`record_type`을 반드시 함께 판단**한다. 모든 지역·검수 값을 확정값으로 가정하지 않는다.

### 5.2 Qdrant/임베딩 원칙

- PR #26의 `A_fixed`, `B_structure` 청크를 입력으로 사용하고, 그 `text`를 임베딩하며 `id`를 포인트 UUID로 재사용한다.
- **청킹 A × 모델 A/B, 청킹 B × 모델 A/B**의 네 실험을 설계한다. 동일 평가 질문·정답 부모 ID·Top-k·검색 조건을 사용한다.
- CPU가 느리면 동일 원본 문서에서 추출한 작은 표본으로 **예비 실험**을 먼저 진행하고, 최종 검증은 가능한 범위의 전체 데이터로 수행한다. 표본 결과를 전체 성능이라고 발표하지 않는다.
- 모델별 차원이 다를 수 있으므로 서로 호환되지 않는 벡터를 같은 벡터 설정으로 섞지 않는다. 컬렉션·모델·데이터 버전·차원·평가 결과를 기록한다.
- 원본 PR #26의 메타데이터가 `metadata` 안에 들어 있으므로 로더가 필터 필드를 올바른 경로에 저장하는지 확인한다. **미검증 지역을 `approved`로 가정하여 필터링하지 않는다.**

### 5.3 Neo4j 원칙

- 최소 노드 후보: `Policy`, `TargetGroup`, `Region`, `SourceDocument`, `GuidelineSection` (시설은 검증된 자료가 있을 때만 추가).
- 최소 엣지 후보: `APPLIES_TO`(정책→대상), `HAS_REGION`(정책→지역), `HAS_SECTION`(문서→섹션), `SUPPORTED_BY`(정책→근거; **검증·승인된 링크만**).
- **정책명·키워드가 비슷하다는 이유만으로 지원 자격·근거 관계를 확정하지 않는다.** 지역 미검증 데이터는 잠정 노드/관계로 구분하거나 적재를 보류한다.
- Graph 없는 검색과 Graph 보강 검색을 동일 질문·근거 예산·프롬프트로 비교한다. 관계가 필요한 질문에서 도움이 되는지 측정하고, 무조건 개선됐다고 주장하지 않는다.

## 9. 실험 및 평가 요구사항

### 9.1 청킹 × 임베딩 2×2 비교

| | 임베딩 모델 A | 임베딩 모델 B |
|---|---|---|
| **A_fixed** (3,400청크) | 실험 1 | 실험 2 |
| **B_structure** (3,865청크) | 실험 3 | 실험 4 |

- **고정:** 가능한 한 동일한 원본 문서 집합, 정답 정책/섹션 ID, 평가 질문, 검색 설정, Top-k, 점수 처리 기준.
- **비교:** Hit@5, Recall@5(복수 정답), MRR@5, 검색 지연시간, 임베딩 시간·비용.
- **대표 표본 예비 실험:** CPU 제약 시 문서/정책과 PDF 섹션을 균형 있게 선정하여 **같은 부모 문서 집합**으로 네 조합 점검. 이는 최종 성능 주장이 아니다.
- **최종 실험:** 여건이 허용하면 전체 청크 기반으로 별도 평가 질문에서 검증. 완료하지 못한 경우 표본 범위·한계·미실행 단계를 명확히 표기.
- **모델 선정 이유:** 한국어 복지 문서 적합성, 검색 품질, 벡터 차원, 실행 환경, 토큰 제한, 비용을 기록.

### 9.2 Neo4j 관계 검색 비교

| 비교안 | 처리 방법 |
|---|---|
| **Graph 제외** | Qdrant 검색 + PostgreSQL 원문·조건 조회 |
| **Graph 포함** | 같은 기본 검색에 Neo4j의 검증된 관계 탐색을 추가 |

동일 질문, 기본 임베딩·답변 모델, 프롬프트, 근거 제공량을 가능한 한 통제하고 **근거 적합성, 관계형 질문 정답률, 응답 시간/비용**을 비교한다. 성능 개선은 테스트 결과로만 판단한다.

### 9.3 LLM/Agent 관련

- LLM은 검색 결과를 바탕으로 답변을 생성하며, 숫자·조건·지역·출처의 누락을 임의 보완하지 않는다.
- 강사 피드백의 **Multi-Agent/Deep Agent 활용 요구**는 설계 및 검토 항목으로 유지한다. 역할을 나눈다면 검색/관계 검증/답변 점검 등 **실제로 구분할 이유와 도구**를 명시한다. 구현 여부는 팀 개발 상태에 맞춰 별도 확정한다.
- 답변 모델·유료 모델을 선택하면 근거(정확도, 모델 제약, 비용 등)를 기록한다.
