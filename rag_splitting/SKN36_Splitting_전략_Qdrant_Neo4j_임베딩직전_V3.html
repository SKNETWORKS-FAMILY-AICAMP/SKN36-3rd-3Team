중앙 461 + 지자체 1,485 = 총 1,946개 정책입니다. 시설은 정책과 별도 검색 데이터이며, PDF 1,189는 정책 건수가 아닌 텍스트 섹션 개수입니다. 지자체 상세 미확보 485건은 원본 목록 정보를 유지하되 신청자격·금액을 생성하지 않습니다.

확인할 내용: PDF 5종 vs 4종

PDF 원본은 5종 존재하지만, preprocess_pdf_01 브랜치의 filtered JSONL에는 4종 1,189섹션만 있습니다. 다섯 번째 노령층 분권 PDF 원본은 별도로 다운로드해 자동 페이지 단위 임시 추출을 할 수 있습니다. 반드시 레이아웃·표·사업별 구조를 검수해야 합니다.

파일을 조사해 찾은 PDF의 특징

1,189개 섹션 모두 JSON 구문 오류·section_id 중복 없이 읽혔습니다. 섹션은 이미 장·절을 보존하지만, 가장 긴 섹션은 약 49,592자에 달합니다. 따라서 PDF를 처음부터 다시 추출하기보다는, 이미 나눈 섹션 안에서 추가로 짧게 쪼개는 것이 합리적입니다.

PDF 파일은 실제 업로드된 guideline_sections_filtered.jsonl을 전수 검사했고, 로컬 파일의 Git blob SHA가 해당 브랜치의 파일과 일치함을 확인했습니다. API 정책 파일은 GitHub의 전처리 스크립트와 품질 보고서로 스키마를 확인했으며, 본 노트북의 정책 실행 테스트는 동일 스키마의 테스트 레코드로 실시했습니다.

03 / 핵심 설계

먼저 ‘내용의 의미’를 나누고, 그다음 ‘길이’를 제한합니다

① 정책 API: 질문 유형별 분리

정책 한 건을 하나의 통문서로 만들지 않습니다.

‘신청방법’과 ‘신청기간’을 같은 청크에 억지로 합치지 않습니다. 1,189개 섹션의 제목 계층·원문 페이지 범위를 유지합니다.

04 / 오버랩을 그림으로

오버랩은 왜 90자를 겹칠까?

긴 설명을 자르다 보면 “소득인정액이…”처럼 조건이 앞 청크 끝과 뒤 청크 시작으로 나뉠 수 있습니다. 그래서 앞 청크 마지막 약 90자를 같은 섹션의 다음 청크에 복사합니다.

청크 A 본문
겹침 90자
겹침 90자
청크 B 본문

두 조각 사이에서만 중복 · 서로 다른 정책이나 PDF 절끼리는 절대 중복하지 않음

지나치게 많이 겹치면 **비슷한 검색 결과가 반복**되고 저장·검색 비용도 증가합니다. 따라서 처음에는 전체 길이의 약 13% 수준인 90자를 사용하되, 필요하면 오버랩 없이 실행한 결과와 비교합니다.

기억할 것

오버랩은 문맥을 도와줄 뿐 정확성을 보장하지 않습니다. 특히 기초연금의 금액·표·예외조건은 원본 페이지를 보고 확인해야 합니다. 같은 문장 일부가 두 청크에 반복되는 것은 의도한 결과이며, 완전히 같은 UUID가 중복되는 오류와는 다릅니다.

05-1 / 데이터베이스 연계

Qdrant는 ‘검색’, Neo4j는 ‘관계’를 담당합니다

청크 크기(정책 650자 / PDF 700자), 오버랩 90자, 섹션 분리 규칙은 변경하지 않았습니다. 이번 변경은 두 데이터베이스가 같은 청크를 가리킬 수 있도록 연결 ID와 관계 파일만 보강한 것입니다.

Qdrant — 질문과 비슷한 문장을 찾기

embedding_ready.jsonl의 text를 나중에 임베딩해 벡터 검색에 사용합니다. id는 고정 UUID로, 그대로 Qdrant 포인트 ID로 사용합니다. metadata는 정책 ID·PDF 출처·지역 필터에 활용합니다.

Neo4j — 문서가 어디서 왔는지 연결하기

neo4j_nodes.jsonl과 neo4j_relationships.jsonl을 출력합니다. 정책→청크, 시설→청크, PDF 문서→섹션→청크의 확인 가능한 소속 관계만 생성합니다.

정책·PDF 원본출처가 있는 내용
→
공통 청크 UUIDQdrant point.id = Neo4j Chunk.id
→
검색 + 관계 확인Qdrant 검색 후 Neo4j 출처 추적

Neo4j 관계 예시

(Policy:정책 ID) ──HAS_CHUNK──▶ (Chunk:청크 UUID)
(PdfDocument:문서 ID) ──HAS_SECTION──▶ (PdfSection:섹션 ID)
(PdfSection:섹션 ID) ──HAS_CHUNK──▶ (Chunk:청크 UUID)

위 관계는 원본 데이터로 확인 가능한 구조만 표현한 것입니다. 정책과 PDF가 같은 사업이라는 관계는 임의로 만들지 않습니다. 승인된 매핑이 생기면 그때 Neo4j에 별도로 추가하세요.

이번 작업은 DB에 저장하는 단계가 아닙니다.

Qdrant는 실제 임베딩 벡터를 만든 다음 업로드해야 하며, Neo4j도 DB 연결 및 제약조건 설정 후 적재해야 합니다. 노트북은 두 DB의 계정 정보나 라이브러리를 요구하지 않습니다. 실제 적재 시 벡터 차원·토큰 제한·Neo4j 제약조건·연결 성공 여부를 별도로 검사해야 합니다.

이번 확장 버전은 (Facility:시설 ID) ──HAS_CHUNK──▶ (Chunk:UUID) 관계를 추가했습니다. 시설 위치·전화번호를 정책의 혜택·자격 요건에 섞지 않으며, 시설이 특정 정책을 제공한다는 관계는 자동 생성하지 않습니다.

수정 버전의 자동 실행 파일을 테스트할 때, 실제 GitHub PDF 전처리 섹션 1,189건과 중앙 461건·지역 1,485건·시설 164건의 동형 테스트 데이터를 사용했습니다. 여기에 5번째 모의 PDF 3페이지를 더해 통합·재실행 안정성, ID 중복, Qdrant↔Neo4j UUID 연결 등을 검증했습니다. 실제 GitHub 중앙·지자체 원문의 전체 내용을 작업환경으로 내려받아 최종 생성 건수를 검증한 것은 아닙니다. 따라서 실제 청크 수는 사용자의 Run All 결과로 확정해야 합니다.

07 / 팀원 인계

다음 담당자에게 넘기는 방식

  1. 데이터 담당자: 입력 JSON/JSONL 4개 파일과 해당 브랜치·커밋 정보를 확정합니다. PDF 5종 중 누락/합본 여부를 확인합니다.
  2. Splitting 담당자: 노트북 첫 코드 셀에서 경로만 설정하고 전체 실행합니다. split_quality_report.json의 건수·제외 수를 점검합니다.
  3. 품질 담당자: pdf_review_queue.csv에서 선정기준·금액·페이지·표를 원본 PDF와 대조하고, 내용이 명백히 불완전한 레코드를 구분합니다.
  4. Qdrant 임베딩 담당자: 모델과 토크나이저를 확정한 후 토큰 길이를 재검사합니다. embedding_ready.jsonl의 id, text, metadata를 사용합니다. 고정 UUID를 포인트 ID로 유지합니다. Neo4j 담당자: 두 관계 파일을 검증 후 적재하고, Chunk 노드의 ID를 Qdrant와 동일하게 유지합니다.
  5. 검색·LLM 담당자: 지역을 모르면 추정하지 않고, 검수된 정책↔PDF 연결만 근거로 사용합니다. 빈자격·미검수 자료는 사용자에게 한계를 표시합니다.
팀 발표용 한 문장

“중앙·지자체 정책 1,946건과 VWorld 시설 164건, 공식 PDF를 자료별 의미 구조에 맞춰 분할하고, 적절한 중첩과 출처·ID 검증을 추가해 향후 임베딩과 근거 기반 검색에 사용하기 쉬운 표준 JSONL로 변환했습니다.”
